## 公众号改写接口：支持本地文件路径输入（节省 token）

### 1. 背景

公众号改写接口 `POST /api/v1/mp/articles/rewrite` 原本要求把每篇原文的正文以字符串形式塞进请求体的 `source_articles[i].content` 字段。在实际使用中存在两个痛点：

- **客户端 token 浪费**：单篇公众号原文动辄上万字，多篇聚合改写时请求体极大，客户端 → 服务端方向的传输 token / 网络带宽被大量消耗；
- **调试不便**：curl / Postman 里直接贴大段中文正文，转义麻烦，也不易复用素材。

因此新增一种传入方式：**客户端只传服务端可读的本地文件路径**（`content_path`），服务端读取该文件内容作为原文正文进入多 Agent 流程。JSON 请求体保持轻量，同一份素材文件可跨多次请求复用。

---

### 2. 设计原则

- **契约先行**：Pydantic 模型层负责表达"`content` 与 `content_path` 二选一"的接口契约；
- **两种方式共存**：兼容原有 `content` 直传方式，不破坏已有调用方；
- **优先级明确**：同时提供时，以 `content_path` 读取到的文件内容为准，`content` 忽略；
- **安全默认**：文件读取路径必须通过白名单根目录 / 后缀 / 大小 三重校验，防目录穿越；
- **下游无感**：服务层在组装 `MpRewriteRequest` 前就把文件内容内联到 `content`，Flow / Task / Agent 层保持零改动。

---

### 3. 数据契约变更

文件：`src/app/schemas/mp_rewrite.py`

`MpArticleInput` 更新为：

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `article_id` | `str` | 否 | 唯一标识，服务端会统一重排为 `art_0/art_1/...`，调用方可省略 |
| `title` | `str` | 否 | 原文标题 |
| `content` | `str` | 条件必填 | 原文正文；若同时提供 `content_path`，以 `content_path` 为准 |
| `content_path` | `str \| null` | 条件必填 | 服务端本地文件路径（如 `.txt` / `.md`）|

模型层校验：使用 `@model_validator(mode="after")` 强制 `content` 与 `content_path` **至少提供一个**，否则直接抛 `ValidationError`，由 FastAPI 返回 422。

---

### 4. 服务层实现

文件：`src/app/services/mp_rewrite_service.py`

#### 4.1 新增读取函数 `_read_article_from_path`

对每个 `content_path` 做四步安全校验后再读取：

1. **路径规范化**：`os.path.expanduser` → `os.path.abspath` → `os.path.realpath`，消除 `..`、软链接绕过；
2. **白名单根目录校验**：若配置了 `APP_MP_ARTICLE_READ_ROOT`，则通过 `os.path.commonpath` 判断规范化后的文件路径必须位于该根目录之下，否则拒绝；
3. **后缀白名单**：默认允许 `.txt / .md / .markdown / .text`，可通过 `APP_MP_ARTICLE_ALLOWED_SUFFIXES` 覆盖；
4. **大小限制**：默认单文件上限 `2 MB`，可通过 `APP_MP_ARTICLE_MAX_FILE_BYTES` 覆盖；
5. **UTF-8 容错读取**：`errors="replace"`，避免个别脏字节导致整体失败。

任何校验失败都抛出 **可读错误信息** 的 `ValueError`，由上层捕获转换成对客户端友好的 `error_message`（HTTP 200 + `code=1`），而不是 500。

#### 4.2 `_normalize_articles` 调整

- 若 `content_path` 非空 → 调用 `_read_article_from_path` 读取正文；
- 否则沿用原来的 `content`；
- 之后统一走原有的**超长截断**逻辑（受 `mp_max_article_chars` 控制，默认 20000 字符）；
- 输出的 `MpArticleInput` 会把 `content_path` 置回 `None`，让下游只看到内联的 `content`。

#### 4.3 入口 `generate_mp_rewrite_report`

- 过滤"两个字段都为空"的原文项；
- 将 `_normalize_articles` 的 `ValueError` 转成 `(None, err_msg)`，走统一错误通道；
- 其它逻辑保持不变。

### 5. 新增配置项

文件：`src/app/core/config.py`（`Settings` 类）

| 环境变量 | 字段名 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `APP_MP_ARTICLE_READ_ROOT` | `mp_article_read_root` | `""` | 允许通过 `content_path` 读取的根目录白名单，空字符串表示不限制（仅开发） |
| `APP_MP_ARTICLE_ALLOWED_SUFFIXES` | `mp_article_allowed_suffixes` | `.txt,.md,.markdown,.text` | 允许的文件后缀，逗号分隔 |
| `APP_MP_ARTICLE_MAX_FILE_BYTES` | `mp_article_max_file_bytes` | `2097152`（2 MB） | 单个本地原文文件最大字节数 |

同时新增 `Settings.get_mp_article_allowed_suffixes()` 用于把逗号分隔字符串解析为规范化的后缀集合（小写、以点开头）。

**生产环境建议配置示例（`.env`）：**

```env
APP_MP_ARTICLE_READ_ROOT=/data/mp/articles
APP_MP_ARTICLE_ALLOWED_SUFFIXES=.txt,.md
APP_MP_ARTICLE_MAX_FILE_BYTES=2097152
```

### 6. API 使用方式

`POST /api/v1/mp/articles/rewrite`

#### 6.1 方式 A：`content_path`（推荐，节省 token）

```json
{
  "rewrite_intent": "面向都市白领，改成轻松易读的公众号推文",
  "target_style": "轻松、生活化、有故事感",
  "source_articles": [
    { "title": "地中海饮食", "content_path": "/data/mp/articles/a1.md" },
    { "title": "备选素材",   "content_path": "/data/mp/articles/a2.txt" }
  ]
}
```

#### 6.2 方式 B：`content`（兼容原有调用）

```json
{
  "rewrite_intent": "面向都市白领，改成轻松易读的公众号推文",
  "source_articles": [
    { "title": "地中海饮食", "content": "……大段正文……" }
  ]
}
```

#### 6.3 混合使用

同一次请求中可以混用两种方式；对单条原文同时提供 `content` 与 `content_path` 时，服务端**优先使用 `content_path`** 的文件内容。

#### 6.4 常见错误返回

以下场景会以 `HTTP 200 + code=1 + message="..."` 的形式返回（不会 500）：

- `content_path 不在允许的目录白名单内: ...`
- `content_path 不存在或不是文件: ...`
- `content_path 文件后缀不被允许: .xxx，允许的后缀: [...]`
- `content_path 文件过大: XXX bytes，上限 YYY bytes`
- `第 N 篇原文读取失败: 读取 content_path 文件失败: ...`
- `所有原文均为空（content 与 content_path 都未提供），无法改写`

字段格式错误（如两者都缺）会由 Pydantic 拦截为 `HTTP 422`。

### 7. 安全性说明

1. **目录穿越防护**：所有路径先 `realpath` 展开软链接，再用 `os.path.commonpath` 与白名单根比较，`..` / 软链接 / 相对路径都无法绕过；
2. **后缀白名单**：默认只允许纯文本类后缀，阻断 `.py / .sh / .pem` 等敏感文件被读取；
3. **大小限制**：默认 2 MB 上限，避免读取超大文件导致内存 / 处理超时；
4. **字符数截断**：读到内容后仍会经过 `mp_max_article_chars` 截断，防止 LLM 上下文爆炸；
5. **错误信息脱敏**：错误消息只回显调用方传入的原始 `raw_path`，不泄露服务端解析后的真实绝对路径。

生产环境强烈建议配置 `APP_MP_ARTICLE_READ_ROOT`。

### 10. 后续可扩展方向

- **URL 输入**：在 `content_path` 之外再支持 `content_url`，服务端主动下载远端文本素材（需配合白名单域名 / 大小限制）；
- **多编码兼容**：目前固定 UTF-8，可扩展 GB18030 / auto-detect（用 `charset-normalizer`）；
- **富文本解析**：允许 `.html` / `.docx` 素材，落到独立的 loader 里做正文抽取；
- **素材缓存**：对同一 `content_path` 做内容摘要缓存，避免重复读取；
- **上传接口**：提供 `POST /api/v1/mp/articles/upload`，先落盘再由改写接口引用，进一步解耦长文素材上传与改写请求。
